# Duration-aware scheduling and calendar/contact exports

The change adds duration-aware availability and URL state, ICS/Google/Outlook exports, and a static mailto feedback form. The planner produces incorrect results on base-zone DST transition days, while its mobile UI prevents choosing most valid starts. Calendar/contact handoffs conflict with privacy copy, long feedback can fail as a `mailto:` URL, and ICS events can collide by identifier. Watch for: **[confirmed]** wrong recommendations and exports on DST dates; **[confirmed]** mobile selection being limited to range openings; **[confirmed]** undisclosed Google/Microsoft transmission; **[likely]** inaccurate webmail wording and long-message failure; **[confirmed]** ICS UID collisions.

**Verdict**: NEEDS_CHANGES

## High-level view

The planner adds elapsed half-hours to local midnight but treats each index as the corresponding wall-clock half-hour. **[confirmed]** After a DST jump or fallback, availability is evaluated at one instant while selection and export resolve another.

Mobile groups candidate starts into ranges, then makes each range one button that chooses only its first start. **[confirmed]** A 09:00–17:00 overlap therefore offers only 09:00 on mobile.

Google and Outlook links place participant labels, local times, and the share URL into third-party query strings. **[confirmed]** This contradicts the site-wide “Nothing you enter is uploaded” statement; **[likely]** registered webmail handlers can likewise receive contact draft data before the user sends it.

The contact form permits 4,000 detail characters in a percent-encoded `mailto:` URI. **[likely]** Browser, OS, and handler limits can truncate or reject the draft without a fallback.

ICS uses only the start and end instants for `UID`. **[confirmed]** Separate meetings at the same time can be deduplicated as the same event.

<summary>Issues (5)</summary>

1. **High — DST candidate drift [confirmed]** — Availability columns advance in elapsed time but selection resolves wall-clock minutes, so transition-day recommendations and exports can target a different instant. Generate wall-clock candidates with an explicit repeated/nonexistent-time policy and add spring/fall regression tests.
2. **High — Mobile start-time lockout [confirmed]** — Each displayed availability range schedules only its opening time, leaving no mobile control for later valid starts. Expose individual starts or a start selector and test a non-first choice.
3. **Medium — External handoff privacy mismatch [confirmed/likely]** — Google/Microsoft receive meeting details when their links open, and webmail may receive contact draft data before send, contrary to blanket local-only wording. Disclose each action-dependent transfer in the UI, footer, and privacy page.
4. **Medium — Oversized mailto drafts [likely]** — The 4,000-character feedback allowance can produce an unsupported URI and lose or truncate the report. Set a tested bound or provide a copy/direct-email fallback.
5. **Medium — Non-unique ICS identity [confirmed]** — Different meetings with identical endpoints get the same UID and may overwrite/deduplicate each other. Add a stable event-specific discriminator and collision coverage.

<summary>Details</summary>

## DST transition days disconnect availability from the chosen meeting

`columns` advances from `dayStart` by elapsed 30-minute increments but records `baseMinutes` as `i * 30` (`src/components/TeamPlanner.tsx:67-91`). **[confirmed]** Spring-forward skips a local hour, so later columns can be labelled one hour earlier than the instant sampled; fallback repeats an hour and omits the end of the local day.

Selection stores `baseMinutes` and reconstructs `meetingAt` with `zonedDateTimeToInstant(viewDate, anchorZone, meetingMinutes)` (`src/components/TeamPlanner.tsx:175-182`). **[confirmed]** Recommendations, “outside hours” badges, and exports can therefore use a different meeting from the green availability state. Generate candidates from local wall-clock values and preserve the resolved instant, with explicit handling for nonexistent and repeated times. Add spring-forward and fallback tests, including a duration spanning the transition.

## Mobile ranges expose only their opening time

`recommendedWindows` collapses runs of candidate starts into ranges (`src/components/TeamPlanner.tsx:102-141`), while the mobile action always calls `setMeetingMinutes(window.startMinutes)` (`src/components/TeamPlanner.tsx:382-417`). **[confirmed]** The desktop grid exposing every start is hidden below `md`, so a card labelled “09:00–17:00” schedules only the configured duration at 09:00.

Render individual starts, add a start selector, or expand each range into its candidates. The accessible name should identify the interval that will actually be selected. Add a mobile interaction test selecting a later start such as 10:30.

## Privacy copy omits external calendar and mail-provider transfers

Google and Outlook URLs include `event.details`: participant labels, local intervals, and the scenario link (`src/lib/time/calendar.ts:71-92`, `src/components/TeamPlanner.tsx:183-201`). **[confirmed]** Opening a link sends those values to Google or Microsoft, while the footer says “Nothing you enter is uploaded” (`src/layouts/Base.astro:288-291`) and the privacy page does not mention calendar providers.

Contact submission navigates to a `mailto:` URI containing the full message (`src/pages/contact.astro:150-173`). **[likely]** A registered webmail handler can receive that payload while creating the draft, before send, contrary to “Your message only leaves the browser if you choose to send.” State instead that the site has no form backend and that clicking an export/email action passes prepared data to the selected provider or mail application.

## Four-thousand-character feedback can exceed mailto limits

The form accepts 4,000 detail characters, adds metadata, and percent-encodes the result into `window.location.href` (`src/pages/contact.astro:57-67`, `src/pages/contact.astro:150-173`). **[likely]** Platform-dependent URI limits can truncate the draft or prevent launch, losing a valid report.

Reduce the allowance to a tested cross-platform bound or provide copy/direct-email fallback behavior. The smoke check only verifies form presence; add a maximum-payload submission test and a fallback-path test.

## ICS identifiers collide for unrelated meetings at the same instant

`buildIcs` uses `UID:hoursapart-${start}-${end}@hoursapart.app` (`src/lib/time/calendar.ts:52-68`). **[confirmed]** Two distinct events with identical endpoints receive the same calendar identity and may be imported as an update or duplicate.

Include a stable discriminator derived from the canonical event/scenario. Test that same-time events with different details have different UIDs while repeated export of one event remains stable.
